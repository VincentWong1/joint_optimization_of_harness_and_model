1. 一句话结论

QwenClawBench 与 OpenHands 不能直接兼容，必须做适配层改造。 该 benchmark 在 harness、Agent CLI、transcript schema、容器镜像、配置文件、grading 几个关键环节都强耦合 OpenClaw（Anthropic Claude Code 的开源克隆），切换到 OpenHands 需要重写 ~30-40% 的代码（约 1000-1500 行 Python），其中 transcript 字段映射和 docker 镜像替换是工作量大头。

3. 底层技术栈

3.1 Agent harness：OpenClaw（不是 LangGraph、不是 OpenAI SDK）

这是整个 benchmark 最核心的耦合点。QwenClawBench 不实现自己的 agent runtime，所有 agent 行为都委托给 openclaw CLI（来自 github.com/openclaw/openclaw）执行。OpenClaw 是 Anthropic 自家 Claude Code 的开源克隆，模型选项写法（dashscope/qwen3.6-plus、anthropic/claude-opus-4-6）也沿用 Claude Code 体系。

核心证据：

  • scripts/lib_agent.py 全文 762 行，全部是 subprocess.run(["openclaw", ...]) 的封装
  • 调用模板：openclaw agent --agent <id> --session-id <sid> --message <prompt>
  • Agent 创建：openclaw agents add <id> --model <m> --workspace <path> --non-interactive
  • thinking level 直接对齐 OpenClaw 的实现：off / minimal / low / medium / high / xhigh / adaptive，并且 xhigh 仅 GPT-5.x 系列、adaptive 仅 Anthropic Claude 4.6 才支持
  • Transcript 路径硬编码到 ~/.openclaw/agents/<agent_id>/sessions/*.jsonl

3.2 隔离层：Docker

scripts/lib_docker.py（594 行）实现 DockerContainer 类，每个任务跑在独立容器：

  • 默认镜像：ghcr.io/openclaw/openclaw:main（OpenClaw 官方镜像，已预装 openclaw CLI）
  • 容器内的 ~/.openclaw 目录从宿主机 openclaw_config/ 拷贝（独立副本，避免并发污染）
  • API key 通过 docker run --env-file 注入
  • 容器内 workspace 固定 /home/node/workspace，所有任务文件 docker cp 进去

3.3 并发与编排

模块实现
并发Python concurrent.futures.ThreadPoolExecutor，每任务一个线程，每线程一个容器

pyyaml >= 6.0.1

注意：仓库本身 Python 依赖只有 2 个，但运行时强依赖 OpenClaw 容器镜像（ghcr.io/openclaw/openclaw:main），整套 agent runtime 都在镜像里。

3.5 评分

  • automated：从任务 markdown 抽 def grade(transcript, workspace_path) -> dict 函数，exec() 执行
  • llm_judge：默认 claude-opus-4-5-20251101，走 OpenAI 兼容 /chat/completions，自带 100 次重试 + 指数退避
  • hybrid：默认带惩罚——auto_score < 0.75 时把 LLM 部分置零（防止 LLM-as-judge 幻觉给虚高分）
  • 统计指标：mean、strict_accuracy（满分率）、pass@k、pass^k

5. 核心实现剖析

5.1 lib_agent.py — Agent 调用层

把 OpenClaw CLI 包装成 Python 函数，关键函数：

  • execute_openclaw_task()：执行单个任务，wraps openclaw agent
  • ensure_agent_exists()：调 openclaw agents add
  • _load_transcript()：读 ~/.openclaw/agents/<id>/sessions/<uuid>.jsonl。注意注释里明确说 OpenClaw 会忽略外部传入的 --session-id，自己生成 UUID，所以这里有一段相当 hacky 的探测逻辑（先查 sessions.json、再 glob 最新文件、最后兜底）
  • _extract_usage_from_transcript()：从 transcript 抽 token 用量和 cost。字段路径：entry.message.usage.{input, output, cacheRead, cacheWrite, totalTokens, cost.total} ← 这是 OpenClaw 的 transcript schema

5.2 lib_docker.py — 容器层

每个任务一个独立容器，每容器一个独立 ~/.openclaw 副本（避免并发污染）：

# /tmp/qwenclawbench/docker_homes/<container_name>
#   └── (.openclaw config 拷贝)
# 容器挂载点: /home/node/.openclaw

docker run -d \
  --name <container> \
  --label qwenclawbench=1 \
  -v /tmp/qwenclawbench/docker_homes/...:/home/node/.openclaw \
  --env-file openclaw_config/.env \
  ghcr.io/openclaw/openclaw:main \
  sleep infinity

workspace 固定在 /home/node/workspace，所有 task asset 通过 docker cp 进入。

5.3 lib_grading.py — 评分层

三种打分模式：

模式实现关键代码
automated从 task md 的 ## Automated Checks 抽出 Python 代码块，exec 后调 grade(transcript, workspace_path)scores 字典取均值得到 [0, 1] 分
llm_judge调 POST {JUDGE_BASE_URL}/chat/completions，prompt 注入 task / expected_behavior / transcript_summary / rubric，要求纯 JSON 输出带 100 次重试，失败回退到 openclaw agent
hybridauto + llm 分别打，按 grading_weights 加权默认惩罚：auto<0.75 → llm=0；--simple-scoring 关闭惩罚

判分函数签名：def grade(transcript: list, workspace_path: str) -> dict。这里的 transcript 是 OpenClaw 的 jsonl 数组，schema 见下节。

5.4 OpenClaw transcript schema（核心耦合点）

评分代码遍历 transcript 时使用以下字段：

# 来自 lib_grading._summarize_transcript() 与 _extract_usage_from_transcript()
{
  "type": "message",
  "message": {
    "role": "assistant" | "user" | "toolResult",
    "content": [
      {"type": "toolCall", "name": "...", "arguments": {...}},
      {"type": "text",     "text":   "..."}
    ],
    "usage": {
      "input": int, "output": int,
      "cacheRead": int, "cacheWrite": int,
      "totalTokens": int,
      "cost": {"total": float}
    }
  }
}

所有 100 个任务的 grade() 函数都基于这个 schema 在判定 tool 调用次数、参数、输出。切换到任何其他 framework，都需要把 transcript 翻译成这套 schema，否则评分代码全失效。

7. 评分机制亮点

7.1 hybrid 惩罚分 ⭐

这套设计很有借鉴价值：

score = w_auto · s_auto + w_llm · s_llm · 𝟙[s_auto ≥ 0.75]

核心思路：当 agent 没把 deliverable 做对（automated 检查不过）时，LLM judge 不论给多高分都置零，避免 LLM judge 被"输出流畅但答错"的 agent 骗过。这是 LLM-as-judge 路线的常见坑（我们 inventory_patrol v3 也踩过类似的合成 GT 翻车），值得在自建评测中复用。

7.2 pass@k / pass^k

  • pass@k：k 次采样中至少 1 次满分的概率
  • pass^k：k 次采样全部满分的概率（更严格）

使用 math.comb 实现 unbiased 估计（参考 HumanEval 那套），相当严谨。

7.3 可恢复执行

支持 --resume、--rerun-anomalous、--no-resume 三种模式，lib_anomalies.py 显式区分 API 错误、容器崩溃、超时——这些都不会被静默折算成分数。这套机制很扎实，也是任何 agent benchmark 必备的工程基础。

8. OpenHands 兼容性评估

8.1 OpenClaw vs OpenHands 关键差异

定位Anthropic Claude Code 开源克隆通用 agent harness（前身 OpenDevin）不一致
调用方式CLI: openclaw agent --message ...Python SDK / Docker server / REST API完全不同
容器镜像ghcr.io/openclaw/openclaw:maindocker.all-hands.dev/all-hands-ai/runtime + sandbox 镜像不兼容

8.2 不兼容点逐一梳理

① 不能直接换镜像

lib_docker.py 默认镜像 ghcr.io/openclaw/openclaw:main 里预装了 openclaw CLI；OpenHands 镜像里没有这个 binary，execute_task_in_docker() 里的 container.exec(["openclaw", ...]) 会全部失败。

② Transcript schema 不一致 → 100 个 grade() 函数全部失效

每个任务的 def grade(transcript, workspace_path) 函数都按 OpenClaw schema 遍历。OpenHands 的 EventStream 是 Action / Observation 对（如 CmdRunAction + CmdOutputObservation），字段名、嵌套结构完全不同。需要写一个 OpenHands → OpenClaw transcript adapter，把：

OpenHands EventStream → 翻译成 →
[
  {"type":"message", "message":{
      "role":"assistant",
      "content":[{"type":"toolCall","name":"bash","arguments":{"command":"ls"}}]
  }},
  {"type":"message", "message":{
      "role":"toolResult",
      "content":["file1\nfile2"]
  }},
  ...
]

否则现有 100 个 grade 函数完全失效。

③ Agent 创建 / 调用 API 不同

OpenClaw：CLI 子命令 openclaw agents add / agent --message。
OpenHands：Python AgentController + EventStream，或者 REST API POST /api/conversations。
lib_agent.py 里 762 行 subprocess 包装代码全部需要重写为 OpenHands SDK 调用。

④ thinking level 无映射

OpenClaw 七档 thinking level 在 OpenHands 里没有对应概念。如果要保留这个功能，需要按模型 provider 各自配置 reasoning effort（如 GPT-5.x 系的 reasoning_effort、Claude 4.6 的 extended_thinking），由 LLM 配置层接管。

⑤ Token usage / cost 字段映射

OpenClaw 字段在 message 内嵌 usage；OpenHands 在 State.metrics 累计。需要在 adapter 里聚合并 reshape。

⑥ Judge 路径需要保留独立

当前 judge 走 OpenAI 兼容 API（已经独立于 OpenClaw），这部分不需要改，是少数几个不需要动的模块。

8.3 兼容点（可复用）

下面这些组件可以原样保留：
  • 任务格式（YAML frontmatter + 5 段 markdown）—— 与 framework 无关，是纯 spec
  • 100 个任务的 prompt / expected_behavior / rubric —— framework 无关
  • workspace assets —— framework 无关
  • LLM judge 引擎（直连 OpenAI 兼容 API）—— framework 无关
  • hybrid 惩罚分公式、pass@k / pass^k 统计 —— framework 无关
  • 异常检测、resume、并发框架 —— 主体逻辑可复用，仅需替换底层调用
  • Docker 容器编排（DockerContainer 类）—— 抽象层基本可复用，只需换镜像和 cmd

9. 迁移到 OpenHands 的工作量评估

9.1 改造路线图

模块改造内容工作量风险
lib_agent.py整体重写为 OpenHands SDK 调用，删除 thinking level 相关代码或映射到对应 provider 参数大（~600 行重写）中（OpenHands SDK 演进快）
lib_docker.py换镜像为 docker.all-hands.dev/all-hands-ai/runtime；workspace 路径改 /workspace；config 从 openclaw.json 换为 config.toml中（~300 行改动）低
lib_grading.py 中 _summarize_transcript + _extract_usage_from_transcript新增 OpenHands EventStream → OpenClaw schema 适配函数，让 100 个 grade() 函数能继续用中（~200 行新增 adapter）高（schema 映射必须完整覆盖所有 ToolCall 类型）
100 个 task md 中的 def grade()不修改 task md，只修改 adapter，让旧函数仍能跑0（关键设计选择）—
config 文件新增 openhands_config/config.toml 和 LLM provider 配置小（~50 行）低
benchmark.py参数解析新增 --harness openhands|openclaw，路由到对应 lib小（~50 行）低

总工作量估算：约 1000-1500 行 Python，1-2 周专人工作（取决于对 OpenHands SDK 的熟悉度）。

9.2 推荐架构（多 harness 通用化）

与其单点替换 OpenClaw → OpenHands，不如借这次重构做成 多 harness 通用 benchmark。这与你 selfDeepAgents 项目里已经在做的 SkillAdapter Protocol 思路天然契合：

┌─────────────────────────────────────────────────────────────┐ │ QwenClawBench 通用化后架构 │ │ │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ HarnessAdapter (Protocol) │ │ │ │ ─ create_agent(model, workspace) -> agent_id │ │ │ │ ─ run_task(prompt, timeout) -> raw_transcript │ │ │ │ ─ to_canonical_transcript() -> CanonicalSchema │ │ │ │ ─ extract_usage() -> {input, output, cost, ...} │ │ │ └──────────────────────────────────────────────────────┘ │ │ ▲ ▲ ▲ │ │ ┌────────┴───────┐ ┌────────┴────────┐ ┌─────┴────────┐ │ │ │ OpenClawAdapter│ │ OpenHandsAdapter│ │ AiderAdapter│ │ │ └────────────────┘ └─────────────────┘ └──────────────┘ │ │ │ │ 100 个 grade() 函数仍按 CanonicalSchema 写，零改动 │ └─────────────────────────────────────────────────────────────┘

关键：引入一个"canonical transcript schema"（建议直接采用 OpenClaw 当前的 schema，因为 100 个 grade 函数已经按它写了），各 harness 实现 to_canonical_transcript()，存量代码全部复用。

10. 建议与结论

10.1 关于直接兼容

不能直接拿 QwenClawBench + 替换镜像就跑 OpenHands。至少要重写 lib_agent + lib_docker，新增 transcript adapter。

10.2 关于该不该迁移

  • 如果只是想评测自家 finetune 的 Qwen 类模型在 OpenHands harness 下的 agent 能力：建议做 OpenHandsAdapter，沿用 100 个 task spec + grade 函数，工作量约 1-2 周。
  • 如果只是想用这套 task 集做能力回归：可以只取 task 的 prompt + expected_behavior，自己用任意 harness 跑，再用 LLM judge 评分（绕开 grade 函数对 transcript schema 的强耦合）。
  • 如果想做 harness 间对比（OpenClaw vs OpenHands vs Aider）：必须做 canonical transcript adapter 路线，工作量较大但价值最高。

10.3 借鉴价值（无论是否迁移都建议吸收）

  1. hybrid 惩罚分公式：auto<0.75 → llm=0，防止 LLM judge 幻觉。这套设计与 inventory_patrol 项目里"合成 GT 翻车"的教训正面契合，建议复用。
  2. pass@k / pass^k 双指标：unbiased 估计法值得直接抄过来。
  3. 异常显式标记：API 错误、容器崩溃、超时不计入分数，是任何严肃 benchmark 必须做的。
  4. 每任务独立 docker 容器 + 独立 ~/.openclaw 副本：彻底隔离并发污染。
  5. resume + rerun-anomalous：长跑必备工程能力。
  6. task 定义用 markdown + YAML frontmatter：grade 函数嵌入 markdown，比纯 YAML 灵活，又比纯代码可读。

10.4 关于评测对象边界

提醒：QwenClawBench 评的是 "模型 + OpenClaw harness + 业务 skill" 的整体系统效果，不是纯 base model 能力。如果换到 OpenHands harness 下跑同样的 task，分数可能差别很大——并不是模型变弱了，而是 harness 不同。这与你项目里 inventory_patrol v0~v3 评测对象的注意点完全一致：必须明确"评的是什么"。
