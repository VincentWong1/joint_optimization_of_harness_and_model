# SQLite
针对你的场景（365 行，1000 列，本地 agent），我觉得有几个比"纯语义分层召回"更靠谱的策略：

**描述增强检索，而非字段名检索** 不要拿原始字段名去算语义相似度。花一次功夫给每个字段写一段简短的业务描述（比如"user_d7_active_days: 用户过去7天内活跃的自然日天数，用于衡量短期活跃度"），然后基于这些描述做语义匹配。描述承载了业务语义，比字段名本身可靠得多。1000 个字段，每个一两句话，总共也就几千字的人工标注成本，但召回质量会好很多。

**预定义查询模式 + LLM 填参** 既然只有 365 行数据，业务场景大概率是相对固定的。你可以把常见的查询意图抽象成 10~20 个查询模板（比如"按时间段聚合某指标"、"找出满足某条件的用户群"、"对比两个维度的趋势"）。LLM 第一层只做意图识别匹配到模板，第二层根据具体 question 填充模板里的字段和过滤条件。这样完全不依赖语义检索，准确率取决于模板设计得全不全。

**LLM 直接做字段选择，不用向量检索** 1000 个字段的 schema（含描述）其实也就几千到一万 token，完全在 LLM 的直接处理范围内。与其让向量模型做粗筛，不如直接把全部字段列表丢给一个轻量调用（甚至可以是同一个模型的快速推理），让它直接输出"这个问题需要用到哪些字段"。LLM 对业务逻辑的理解比向量相似度灵活得多，而且如果输出有遗漏，你可以通过 prompt 工程或者 few-shot 示例来纠偏。

**宽表保留 + 给 LLM 看样例数据** 365 行数据量极小，其实没必要为了查询效率拆表。更关键的是让 LLM"知道"表里有什么。你可以在 prompt 里附上几行脱敏的样例数据，让 LLM 从真实数据里推断字段含义和相关性，而不是只看字段名。有时候 LLM 看到一行真实数据，比看 1000 个字段名更能准确判断该查什么。

这几种方案不是互斥的。我自己的话可能会这样组合：`给每个字段写业务描述 → 预定义高频查询模板覆盖 80% 的场景 → 对于剩下的长尾查询，把完整字段描述列表 + 几行样例数据一起丢给 LLM 直接选字段 → 生成 SQL` 。
