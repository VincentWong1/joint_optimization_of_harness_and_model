NL2SQL Agent 架构对比 (2026)

是否用更新方案替代当前的 nl2dsl → dsl2sql 两阶段管线？面向 ODPS / MaxCompute 的可行性结论 · 2026-05-20

数据库：ODPS / MaxCompute 基线：两阶段 + Schema Linking 权重：稳定性 / 扩展性 / 延迟成本 资料窗口：2025-12 起

结论 (TL;DR)

建议：去掉 DSL 中间层，直接演进为「Schema Linking → 直生 ODPS SQL → 有界执行反馈」三段式架构，并直接复用阿里集团内的 XiYan-SQL / M-Schema / Spring AI Alibaba NL2SQL 资产。

2026 上半年学界已经给出明确信号：ReViSQL 用 RLVR + 干净训练数据，在 BIRD-Verified Mini-Dev 上拿到 93.2% 执行准确率，首次超过人类水平（92.96%），且 30B-A3B 版本以 7.5× 更低单查询成本就能匹配此前 SOTA（arXiv:2603.20004）。这意味着「靠堆 Agent 复杂度提升准确率」的范式已经走到尽头 — 现在是简化架构的时机，不是叠加。

  • 不再需要 DSL：DSL 是 GPT-3.5 时代弱模型的补丁。2026 主流大模型（Claude 4.x / Qwen3-Max / GPT-4.5 / Gemini 2.5 Pro / DeepSeek-V3）已能直生 ODPS 方言，DSL 反而成为表达力瓶颈。
  • 不上无界 Agentic Loop：CHESS / MAC-SQL 类多 Agent 反思可在 BIRD 上再涨 3–5 pp，但代价是 5–20× token、5–30 s 延迟、产出不可复现 — 与「稳定 / 成本」约束冲突。
  • 不直接 all-in MCP：MCP 在 2026 已成事实标准（Linux Foundation AAIF + 1000+ servers），但适合开发者交互式探索，作为线上批量分析后端会丢失审计/限流/缓存能力。
  • 正解：保留 Schema Linker（用 M-Schema 风格）+ 加 RAG 历史 SQL 检索 + 直生 SQL + Validator + 最多 1–2 次 Refiner。把现有 dsl2sql 规则降级为 Validator 的方言 lint 规则。

1. 当前基线：nl2dsl → dsl2sql

用户自述：Stage 1: NL + schema → 结构化 DSL（intent / entities / filters）；Stage 2: DSL + 方言规则 → ODPS SQL。痛点：DSL 文法维护、schema linking 准确率。

NL ──► [LLM: nl2dsl] ──► DSL (JSON) ──► [Rule: dsl2sql] ──► ODPS SQL ▲ ▲ schema embeddings dialect rules (Hive/MaxCompute)

这条路线的历史价值

  • 当模型 ≤ GPT-3.5 / Qwen-7B 时代，直生 SQL 出错率高 — DSL 缩小了「指令 → 可执行」的搜索空间。
  • DSL 提供天然的可审计 / 可回放层，便于风控、限流、变更追踪。
  • 方言规则集中可维护，跨数据源时只换 codegen 后端。
  • 对应 Text-to-SQL 演进的「第二代 NLU 范式」（参考 CSDN 2026 综述提到的四代演进）— 在大模型出现前的最优工程妥协。

2026 现在的三个瓶颈

  • 表达力天花板：DSL 难以覆盖窗口函数、UDTF、`LATERAL VIEW EXPLODE`、半结构化 JSON 抽取、ODPS 2026 新增的 Auto Partition / UNNEST / Delta Table MERGE INTO 多次 update+insert 等特化语法 — 一定要扩 DSL，规则爆炸。
  • 双重失真：NL→DSL 错率 × DSL→SQL 漏配率 = 累乘损失，且错误归因困难。
  • 新业务 onboarding 慢：每个新指标 / 新口径都要补 DSL slot，业务等不起；而 RAG-based 框架（如析言 GBI）只要喂业务问答样例就能在线扩展。

3. 可选架构家族（5 类）

A. 单次直生 LLM + 强 Schema Linking

代表：RSL-SQL（双向 schema linking）、OmniSQL（开源 SFT）、LitE-SQL（向量化 schema 检索）。

NL ──► [Schema Linker: 选表/选列/外键召回] ──► [LLM: 直生 SQL] ──► SQL (M-Schema / DDL + samples + value retrieval)

2026 关键事实

  • BIRD-dev 70–75 EX 区间稳定可达；Spider 1.0 已基本饱和（> 88）。
  • 延迟 1–3 s，token 1×（最低）。
  • 瓶颈在 Schema Linker：千表万列规模下，传统数据库级 schema linking 不可扩展（AutoLink 要解决的问题）。

稳定性 ★★★★延迟成本 ★★★★★复杂查询 ★★★

B. Multi-Generator 集成（XiYan-SQL 范式）

代表：XiYan-SQL（阿里）、MCS-SQL、R²-SQL、CA-SQL。核心是「生成多候选 → 排序 / 投票 → 选优」。

NL ──► Schema Filter ──► ┌─ Generator (ICL, prompt-A) ─┐ ├─ Generator (ICL, prompt-B) ─┤── Refiner ──► Selector ──► SQL └─ Generator (SFT) ───────────┘

2026 关键事实

  • XiYan-SQL 的 multi-generator 是目前工业落地最成熟的范式：BIRD 75.63%、Spider 89.65%、阿里云析言 GBI 已商业化。
  • R²-SQL 改进了选优阶段（Ranking Reward），开源 SOTA 75.03%。
  • CA-SQL 让难度自适应 — 简单题少跑，难题多跑，token 成本平摊后只比单生成器高 1.5–3×。

稳定性 ★★★★延迟成本 ★★★复杂查询 ★★★★

C. Execution-Aware Agentic Loop

代表：ReEx-SQL（解码中穿插执行 + RL）、ReViSQL（推理时执行对账 + 多数投票 + RLVR）、CHESS、MAC-SQL、SEA-SQL。

NL ──► Schema Linker ──► [Generator ──► Executor ──► Reviser]* ──► SQL ▲ │ └── 错误信息 / 空结果 / 部分结果 ◄─────┘

2026 关键事实

  • ReViSQL 的颠覆性结论：架构复杂度已不再是答案。它用相对简单的执行对账 + 多数投票，凭借 BIRD-Verified 干净数据，达到了人类水平。
  • 无界 reflect-fix 循环延迟可达 5–30 s，且同问两次产 SQL 不同 — 不可复现，与生产稳定性约束直接冲突。
  • HN 上 IDinsight 2024 的反向案例 "Using Agents to NOT Use Agents" 印证：生产团队把 Agent 砍回伪 Agent 流水线换稳定性。

稳定性 ★★延迟成本 ★★复杂查询 ★★★★★

D. MCP-based DB Agent

2026 现状：MCP（Anthropic 2024-11 推出）已被 OpenAI / Google / Microsoft 采纳，捐赠给 Linux Foundation 旗下 Agentic AI Foundation (AAIF) 中立治理，1000+ 开源 server。Azure AI Search 在 2026-04-01 REST API 中正式 GA agentic retrieval，每个 knowledge base 都暴露 MCP endpoint。

NL ──► [LLM with MCP tools] ├─ list_tables / describe_table / sample_rows ├─ explain_plan └─ execute_sql ──► DB ▲ 多轮工具调用 + LLM 自行规划

2026 关键事实

  • Postgres / MySQL / Snowflake / BigQuery / DuckDB 都有公开 MCP server；ODPS / MaxCompute 暂未见稳定的官方 MCP server（截至本次搜索 2026-05）。
  • HN 上 DataFrey – MCP server for Snowflake with text-to-SQL agent 是同类商业化样本。
  • 适合开发者交互式查询；用作线上批处理后端缺审计 / 限流 / 缓存。

交互探索 ★★★★★线上稳定 ★★需自建 ODPS-MCP

E. RAG-based 框架（含阿里析言 GBI / Spring AI Alibaba）

代表：Vanna.AI（agentic retrieval text-to-SQL，github 主流框架）、DB-GPT（中文社区）、WrenAI、Dataherald、AskTable。阿里也在这条路线上： spring-ai-alibaba-nl2sql 是阿里云百炼 / 析言 GBI 把「Schema 召回 + SQL 生成 + SQL 执行」核心链路开源给 Java 开发者的项目。

2026 关键事实

  • 核心机制：把历史正确 SQL + 业务术语 + DDL 做向量检索作为 few-shot — 外置长期记忆。
  • 对新表 / 新口径的扩展性最好：喂样例即涨点，无需改代码或微调。
  • 缺点：质量上限受检索质量限制；对从未问过的复杂查询无加成。
  • 大部分公开框架默认是 PG / MySQL / Snowflake，ODPS 方言适配需要自己写 dialect 模板 — 但 spring-ai-alibaba-nl2sql 与析言 GBI 已经踩过这条路。

扩展性 ★★★★★稳定性 ★★★★复杂查询 ★★★

5. ODPS / MaxCompute 特定考量

2026 方言与平台演进

  • MaxCompute 4.0（2025）已是「AI Native 平台」，CPU/GPU 统一调度，峰值 50 亿次/秒，支持湖仓一体 + 多模态 + Object Table。
  • 新增 BigQuery 兼容模式（odps.sql.bigquery.compatible），支持 Auto Partition、UNNEST、Delta Table MERGE INTO 多次 update+insert、DELETE FROM 别名、30+ 内建函数 — 这些 DSL 几乎不可能跟得上。
  • MaxFrame Python 框架 + SQL 调用 AI 函数，让 SQL 本身就能嵌入大模型推理。

规模与组织约束

  • 真实工业 schema 通常上千张表 + 中文业务术语 — Schema Linker 必须支持中文同义词扩展。
  • 分区谓词是硬约束：无分区过滤 = 全表扫描 + 高额账单。Validator 必须强制检查。
  • 权限走 RAM / MaxCompute Project — Validator 之前加 ACL pre-check（不让 LLM 看到无权限表）。
  • 跨系统迁移参考阿里内部 GoTerra 项目（10 万+ SQL 转写），方言差异是主要工程量。

已有 / 内部资产（务必复用）

  • XiYan-SQL（github XGenerationLab/XiYan-SQL，994⭐，2026-05-05 last commit）— 阿里集团自研，方言原生支持。
  • M-Schema（github XGenerationLab/M-Schema）— 半结构化 schema 表示，可单独引入到现有管线。
  • spring-ai-alibaba-nl2sql（github alibaba/spring-ai-alibaba）— 析言 GBI 把 Schema 召回 + SQL 生成 + 执行核心链路开源给 Java 开发者，2025 起持续迭代。
  • 析言 GBI 对接 Hologres / MaxCompute 已有成熟产品形态，可作为 reference 实现。
  • 你现有的 dsl2sql 规则集不要丢 — 把它降级为 Validator 的 dialect lint 规则源。

风险与边界

  • 不要让 LLM 直连生产 ODPS（即便有 MCP）。所有产出 SQL 必须经 Validator + dry-run + ACL 检查再执行。
  • 对写入 / DDL / DELETE / TRUNCATE / 删除分区建立强黑名单，无视 LLM 意图。
  • 对大表全表扫描设置成本阈值（按 explain 估算输入量），超过即拒答 + 反向提示用户加分区谓词。
  • 多模型路由：高频简单题用 Qwen3-7B/Haiku 4.5，长尾难题升级到 Opus 4.7 / Qwen3-Max — 单次成本可降 5–10×。

6. 推荐架构与渐进式迁移路径

推荐架构 F（混合）— 直接复用阿里集团资产

NL │ ▼ [Schema Linker] ◄── M-Schema 表示 + 业务术语 KB + 历史 SQL 检索 (RAG) │ (返回候选表/列/外键/示例值) (复用 XGenerationLab/M-Schema) ▼ [Template Cache?] ──hit──► 直接返回参数化 SQL ─► 跳到 Validator │ miss ▼ [LLM: 直生 ODPS SQL] ◄── few-shot：高频模板 + ODPS dialect 卡片 │ （base 可选 Qwen3-Max / Claude 4.7 / DeepSeek-V3） ▼ [SQL Validator] ── parse / dry-run / 分区谓词 / 黑名单算子 / ACL │ pass ───────────────────────────────────────────────────────────► 执行 │ fail (≤ 1–2 次) ▼ [Refiner] ── 错误信息 + 列子集回喂 LLM 修补 │ ▼ (仍失败) [Hard-Mode 多生成器] ── 仅困难/失败请求；ICL+SFT 多 candidate + Selector （直接 fork XiYan-SQL，不重写） 超时熔断 / 并发限流 / 成本上限

4 阶段迁移路径

  1. 阶段 1 (1–2 周)：Validator 抢救层。 把现有 dsl2sql 规则全部抽到独立 SQL Validator（parse → dry-run → 分区检查 → ACL → 黑名单）。这是后面所有架构的公共下游。已有规则的 ROI 在这里继续兑现。
  2. 阶段 2 (2–3 周)：M-Schema + 直生 SQL。 直接 fork XGenerationLab/M-Schema，加 RAG 检索（DDL + 业务术语 + 历史正确 SQL）。LLM 直生 ODPS SQL → Validator。保留旧 nl2dsl 路径作为 fallback，AB 评估。
  3. 阶段 3 (3–4 周)：模板缓存 + Refiner。 高频问题做参数化模板缓存（70% 流量提速到 ~50 ms）。Validator 失败时进入 Refiner（≤ 2 轮，错误信息回喂同一 LLM）。
  4. 阶段 4 (按需)：Hard-Mode + 内部 MCP 工作台。 困难请求或长期失败请求 → fork XiYan-SQL multi-generator pipeline 兜底；同步给数据分析师配 ODPS-MCP 探索工作台（用 Claude Code / Cursor 直接连库），不进生产路径。

明确反对的做法

  • 不要直接把 nl2dsl→dsl2sql 整个换成无界 Agent — 稳定性回退、产出不可复现。
  • 不要把 ODPS 直接通过 MCP 暴露给 LLM 作为生产入口 — 缺审计与限流。
  • 不要仅靠 RAG（Vanna 风格）就上线 — 复杂查询天花板低。
  • 不要从零做 NL2SQL 专用模型 fine-tune — 工程成本远高于「prompt + RAG + 复用 XiYan」。除非你能维持 BIRD/Spider eval pipeline，且团队有 RL infra。
  • 不要叠加更复杂的 Agent 架构 — ReViSQL 已经证明架构复杂度不再是 BIRD 上的差距来源，训练数据质量才是。

评估指标（一并迁移）

  • 线下：BIRD-dev EX、Spider 2.0 EX、自家黄金集 EX (Execution Accuracy) + EM (Exact Match)。考虑接入 BIRD-CRITIC（XiYan 已刷 SOTA）做难度分层评测。
  • 线上：首字延迟 P50/P95、Token cost / Q、Validator pass rate、Refiner 触发率、人工接管率。
  • 消融：Schema Linker 单独的 Recall@K — 这是最大的稳定性来源，必须长期监控。

7. 结论：是否替换 DSL 管线？

是。但是用最便宜的方式替换。

  1. 「模型基座能力进化」与「Agent harness 改良」都已发生，但意味着的不是「上更复杂的 Agent」，而是「不再需要 DSL 这个补丁」 — Qwen3-Max / Claude 4.7 / GPT-4.5 等 2026 主流模型已能直生 ODPS 方言，DSL 已成累赘。
  2. 2026 H1 的 ReViSQL 结果是路线判断分水岭：BIRD 已被攻克到人类水平，且关键变量是数据质量而非架构复杂度。继续把 Agent 做复杂没有 ROI。
  3. 对你（ODPS 用户）最可行的方案是 F. 混合架构：Schema Linking + 直生 SQL + Validator + 有界 Refiner，把 dsl2sql 规则降级为 Validator lint，把 nl2dsl 整个移除。落地路径已成熟（XiYan-SQL / M-Schema / spring-ai-alibaba-nl2sql 都是开源资产）。
  4. 不必做 fine-tune，不必做 MCP-first 改造，不必上无界 Agent 循环。这三个都不是当下的最佳折中。
