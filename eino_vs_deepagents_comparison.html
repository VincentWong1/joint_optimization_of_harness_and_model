cloudwego/eino vs DeepAgents

Harness 框架选型对比 · 面向「Claude Code 兼容 + 垂域 Agent rollout 收集 trajectory + 用 trajectory 做 harness self-improve & 基座 fine-tune」三重需求 · 2026-05-21

语言：Go vs Python 权重：Claude Code 兼容 / Trajectory / Fine-tune 闭环 资料窗口：2025-12 起

结论 (TL;DR)

三项需求下 DeepAgents 完胜，建议作为主框架。eino 仅在「上线后做高并发线上推理服务」时才有压倒性优势 — 这与你三条需求的方向都不在一条主线上。

  • Claude Code 兼容：DeepAgents 设计上就是「Claude Code 范式的开源 batteries-included harness」 — planning、virtual filesystem、subagent、long-horizon task 四件套逐个对齐 Claude Code 的内部架构，工具命名（write_todos ≈ TodoWrite，read_file/write_file/edit_file ≈ Claude Code File 工具）甚至都对齐了。eino 是通用 Go LLM 编排框架，要做 Claude Code 兼容得自己造轮子。
  • Trajectory 数据：DeepAgents 跑在 LangGraph 1.0 之上，每一次 state transition 都有原生 checkpoint，配套 LangSmith 直接落 trace；中间件机制让你不改业务代码就能挂 trajectory logger。eino 有 CloudWeGo DevOps 可视化调试，但 trajectory 数据导出要自己用 callbacks 写适配层。
  • Fine-tune 闭环：Python 生态就是 ML 训练事实标准 — DeepAgents → LangSmith trace → HuggingFace TRL / OpenRLHF / Unsloth / ART / Verifiers 都是直连。eino 的 Go trajectory 必须先序列化导出再交给 Python 训练管线，跨语言桥接是常态化的额外工程。
  • 什么时候反而该选 eino：当你同一套代码既要做 R&D 又要直接上生产线上服务，且并发量高、对延迟和单机吞吐敏感、运维资源紧 — 这时 eino 的「单一 Go 二进制 + 高并发原生 + 字节内部生产验证」组合是 Python 给不了的。但这不在你这三条需求里。

务实方案：DeepAgents 做 R&D / 数据收集 / 训练闭环；若日后要把同一套 Agent 业务上生产线上服务且压测吃不消，再用 eino 在关键热路径上重写（这是字节内部已有的常态化分工模式）。

1. 两个框架是干什么的

Go cloudwego/eino

字节跳动 CloudWeGo 生态的 LLM 应用编排框架

  • 定位：「Go 语言的终极 LLM 应用开发框架」，填补 Python (LangChain/LlamaIndex) 在 Go 生态的空缺。
  • 核心抽象：组件（Component）+ 编排（Graph/Workflow/Chain）+ 流式（Stream）+ 类型安全（编译期）。
  • 四阶段演进观：Prompt → LLM+Tool → ReAct → Multi-Agent，框架核心给后三者提供编排。
  • 生态搭子：与 Kitex (RPC)、Hertz (HTTP)、Eino DevOps（可视化调试 / Trace）配套，面向工程稳定性而非 R&D 速度。
  • 已落地场景：字节、腾讯、蚂蚁、Shopee 等公司主力生产语言的 Go 微服务里嵌入 LLM 能力。

工程稳定性 ★★★★★ 部署运维 ★★★★★ R&D 速度 ★★★ ML 生态集成 ★★

Python DeepAgents (LangChain 官方)

LangChain 1.0 / LangGraph 1.0 配套的「Claude Code 范式」开源 harness

  • 定位：「The batteries-included agent harness」 — 把 Claude Code 内部架构开源给所有人用。
  • 四件套内置：① 规划（write_todos/read_todos，强制先写 TodoList 再执行）② 虚拟文件系统（read_file/write_file/edit_file/ls/glob/grep，避免 Context Rot）③ 子智能体委托（任务隔离 + 上下文隔离）④ 长期记忆持久化。
  • 中间件机制：ToolSelector / TodoList / FileSystem 中间件可热插拔；可挂任意 LangGraph 节点。
  • 底层：LangGraph 1.0（图编排 + checkpoint + Human-in-the-Loop）+ LangChain 1.0（model/tool/memory 抽象）+ LangSmith（trace/eval/replay）。
  • 已落地场景：Open Deep Research、AgentTeam2026、客服 Agent、长 horizon 自动化任务，面向 R&D 速度和能力深度。

Claude Code 对齐 ★★★★★ R&D 速度 ★★★★★ ML 生态集成 ★★★★★ 线上吞吐 ★★★

2. 逐项需求对比

需求 1需要一个和 Claude Code 兼容性比较好的 harness 框架

什么叫"Claude Code 兼容"

不是简单"能调 Claude API"（那 LiteLLM / OpenAI SDK 都行）。真正的兼容是架构对齐：你的 Agent 行为模式、prompt 结构、工具命名、控制流，能与 Claude Code 的设计哲学无缝迁移；微代理（microagent）、planning tool、subagents、virtual file system 这些概念在你的框架里有一一对应。

Claude Code 内部组件DeepAgents 对应eino 对应
TodoWrite (planning tool)原生 write_todos / read_todos 工具 + TodoList 中间件需要自己实现一个 Tool 注册
Read / Write / Edit / Glob / Grep (file tools)FileSystem 中间件原生提供 read_file/write_file/edit_file/ls/glob/grep需要自己实现，且 Go 的文件系统抽象偏 OS-native
Subagent / Task delegation原生 sub-agent 子图机制（LangGraph 子图）eino 的 Multi-Agent 编排能做，但样板代码更多
Long-horizon system promptDeepAgents 默认 prompt 就是"参照 Claude Code" 写的（README 明示）完全靠你自己设计
MCP Server 接入LangChain 1.0 原生支持，langchain-mcp-adapters 即插即用eino 有 MCP 支持，但社区 Server 多用 Python/TS 实现 — 生态偏弱
Microagent（关键词触发的 skill pack）可用 ToolSelector 中间件近似实现，但没原生概念需要自己造

结论 1：DeepAgents 是 Claude Code 范式的「开源同源框架」，迁移和复现成本接近 0；eino 是「通用 LLM 编排框架」，Claude Code 兼容需要自己造整套适配层，工作量大概要 2–4 周资深工程师。

需求 2该框架适合做垂域实际应用场景的 agent rollout，获得 trajectory 数据

Trajectory 数据是什么

对 RL / SFT 训练有用的最小数据单元是 (state_t, action_t, reward_t, state_{t+1}) 序列。对 LLM Agent 来说就是「每一步的完整 prompt + tool call + tool result + intermediate output」可追溯、可重放、可注释。

能力DeepAgentseino
State 持久化（checkpoint）LangGraph checkpointer 原生支持，Postgres/Redis/Memory 三种后端，每个 node transition 自动落盘CloudWeGo DevOps 提供 trace 可视化，但 trajectory 持久化要自己 hook callbacks
Human-in-the-Loop (打标 / 标注 reward)LangGraph interrupt 原生支持，可在任意节点暂停等人工标注需要自建中断 / 标注 UI
Trace 可视化与 ReplayLangSmith 原生 — 鼠标点开就能看每一步 prompt/response/tool_call/error，可一键 replayEino DevOps 提供，但比 LangSmith 生态成熟度低
多轮会话 / 长 horizon trajectoryDeepAgents 文件系统中间件专门解决 Context Rot — 长 trajectory 不会爆 context需要自己设计 context 压缩 / 外置存储
导出为训练样本格式LangSmith 一键导出 ChatML / JSON / Parquet；langsmith.Client().list_runs() 直接遍历trace 是 Go 内部结构，要写自定义 exporter 序列化成训练样本
线上灰度 + A/B Agent 版本LangGraph Cloud / Self-host server 支持，但生产级 SLA 需要工程加固Go 单一二进制 + 字节内部生产经验，灰度路由更稳

结论 2：R&D 期的 trajectory 收集，DeepAgents 几乎零工作量。eino 在「线上服务化 rollout」吃稳定性优势，但本需求更强调"获得 trajectory 数据"，DeepAgents 的 LangGraph checkpoint + LangSmith 组合是事实标准，没有同等位面对手。

需求 3基于 trajectory 数据做 harness self-improve 和基座 LLM 的 fine-tune

这一步决定要什么生态

RLHF / RLAIF / DPO / GRPO / SFT 这一切的事实标准都是 Python：HuggingFace TRL、Unsloth、OpenRLHF、Anthropic 的 ART (Agent RL Toolkit)、prime-rl Verifiers、AllenAI Open-Instruct、vLLM/SGLang 等。Go 在这条赛道没有可用的训练栈。

训练管线环节DeepAgents (Python)eino (Go)
从 trajectory 抽取 prompt-response 对LangSmith API 直读 → pandas DataFrame → TRL Dataset，3 行代码Go trace → JSON 导出 → Python 加载 → 转 Dataset，跨语言桥
SFT 训练直接 SFTTrainer(model, dataset)先解决数据格式 + 跨语言问题，再 Python 训
PPO / DPO / GRPOTRL 原生 + Verifiers / OpenRLHF同上 — 必须切回 Python
Agent RL（多步 trajectory 直接训）ART / Verifiers 直接吃 LangGraph trajectory，同进程闭环同上
Harness self-improve（让 Agent 自己反思+改 prompt+改 microagent）中间件机制让你把"reflect → patch prompt → 写回中间件"做成一个 LangGraph 节点，闭环完整在 Python 内需要在 Go 和 Python 之间反复同步状态
训后模型推理回灌vLLM/SGLang/Ollama 全开 OpenAI 协议，DeepAgents 直接配 base_url 切换eino 同样能配，模型推理这一步两边都没问题

结论 3：DeepAgents 把"收集 → 训练 → 回灌"做成同一进程同一语言闭环。eino 必须在中间架一座 Go ↔ Python 桥，这桥就是个常态化的维护负担。选择 eino 等于人为给训练闭环加一道工程墙。

4. 推荐架构：DeepAgents 为主 + eino 待命

近期（0–6 个月）：DeepAgents-only 闭环

┌────────────────────────────────────────────────────────────────┐ │ DeepAgents Harness（Python） │ │ ┌─────────────┐ ┌──────────────┐ ┌───────────────┐ │ │ │ Planning │ │ FileSystem │ │ Sub-agents │ │ │ │ (TodoList) │ │ (vfs) │ │ (task split) │ │ │ └─────────────┘ └──────────────┘ └───────────────┘ │ │ │ │ │ ▼ │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ LangGraph 1.0 ← checkpointer (Postgres) ← rollout 状态机 │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ every node transition │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ LangSmith trace / replay / human label │ │ │ └────────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ export (Parquet / ChatML) │ │ ┌────────────────────────────────────────────────────────────┐ │ │ │ TRL / Verifiers / ART → SFT / DPO / Agent RL │ │ │ │ ↓ │ │ │ │ 训后 base model → vLLM serve → 回灌进 DeepAgents (闭环) │ │ │ └────────────────────────────────────────────────────────────┘ │ └────────────────────────────────────────────────────────────────┘
  • Week 1–2：装 LangChain 1.0 + LangGraph 1.0 + DeepAgents + LangSmith；用你最熟悉的 1 个垂域任务跑通最小 ReAct Agent。
  • Week 3–4：挂上 TodoList + FileSystem + ToolSelector 三个中间件；接 1 个 MCP server 验证 Claude Code 风格工具调用。
  • Week 5–8：垂域 rollout 上量；LangSmith 抓 trace；用 langsmith.Client().list_runs() 自动导出训练样本。
  • Week 9–12：起 TRL SFTTrainer 跑 baseline；起 Verifiers / ART 跑 Agent RL；训后模型 vLLM serve 回灌 DeepAgents 对照评估。

中长期（6 个月后，仅在必要时）：eino 作为生产推理后端

如果你的 R&D 成熟到需要把同一套 Agent 业务大规模上线服务化，且 Python harness 在压测下吃不消（典型阈值：QPS > 500，P99 < 1.5 s 强制 SLA），这时把已经验证好的 Agent 流程用 eino 在 Go 端重写关键热路径。

  • R&D 训出来的模型用 vLLM/SGLang 起 OpenAI 兼容服务，eino 通过 base_url 接，模型层共用。
  • Agent 编排层在 eino 重写，复用 Python 端验证好的 prompt/tool 定义。
  • 这是字节内部已成熟的分工模式：R&D 用 Python (LangChain) + 上线用 Go (Eino)。

反直觉提醒：很多团队一开始就想"用 eino 一次性搞定 R&D + 上线"，结果 R&D 阶段被类型系统、Go 缺少 ML 库、缺少 Jupyter 等问题拖慢 2–3 倍。先用 Python 跑通业务，再决定要不要 Go 重写。

5. 明确反对的做法

  • 不要仅靠 eino 跑通整个「rollout → trajectory → fine-tune」闭环 — 跨语言桥的维护成本会持续消耗团队精力，且 Go 生态没有 TRL/Verifiers/ART 这类训练库。
  • 不要同时用 eino + DeepAgents 维护两套并行的 Agent 业务代码 — 业务 prompt/tool 定义会快速漂移；只能"一个语言主导业务定义，另一个语言只做推理服务转译"。
  • 不要把 DeepAgents 当 production-grade 高并发服务直接对外暴露 — LangGraph Cloud / 自建 LangServe 适合中等并发。要扛流量峰值需在前面加缓存 / 队列 / 限流。
  • 不要自己从零基于 LangGraph 重新造一套 Claude Code 兼容层 — DeepAgents 已经做好了，Re-invent the wheel 的成本不值。
  • 不要跳过 LangSmith 直接用 stdout/日志做 trajectory 收集 — 你需要的不只是日志，而是结构化 trace + 可 replay + 可 diff + 可标注，这些自己造要数月。
